## 1. Purpose

Declare the Plugin category's boundary and complete planned `WP-ERROR` entry set *before* any new entry in it is authored, per **SF-SPEC-013** Section 5.1's Category Entry Criteria — the third candidate in the Knowledge Production Plan's roadmap, and the first category this project has entered with an existing, unbaselined entry (`WP-ERROR-017`) already present rather than starting from zero, the same situation Database and PHP Runtime were in before this project began declaring taxonomies in advance.

This document does not itself contain any `WP-ERROR` knowledge content and is not cited as a `WP-ERROR` entry. `WP-ERROR-017` predates this taxonomy; Section 3 treats it as an existing, already-Production-Ready entry whose own boundary this taxonomy shall account for rather than redefine.

## 2. Category Boundary

**Plugin** (referred to in this project's own informal roadmap as "Plugin Lifecycle") owns failures in WordPress core's own generic mechanisms for managing plugin code across its lifecycle — loading, activation, dependency-requirement enforcement, and update — and the fatal errors or inconsistent states those specific mechanisms can produce. It does not own arbitrary business-logic defects inside a specific third-party plugin's own code, once that plugin is running normally through a lifecycle stage that itself completed correctly.

This distinction matters because "Plugin category" is cited, generically and without a specific `WP-ERROR` ID, by numerous entries in this repository (`WP-ERROR-013`, `016`, `022`, `023`, `024`, `026`, `027`; `SF-TAXONOMY-001`–`004`) as the destination for "a specific plugin's own implementation defect" or "a specific plugin's own coding defect." Those citations are accurate as attributions (the defect genuinely does not belong to the citing entry), but they are not a catalog obligation this taxonomy can fulfill — a specific plugin's own arbitrary business-logic bug is not a reproducible, WordPress-mechanism-level condition this framework's methodology can document the way it documents `wp_authenticate()` or `WP_REST_Server` behavior. This taxonomy instead claims the territory those citations actually gesture toward when examined closely: not "any bug in any plugin," but WordPress's own generic, mechanism-level plugin-management behavior — the same behavior every plugin, well-written or not, passes through.

**Explicitly not owned by Plugin:**

* **A specific plugin's own business-logic defect, once loaded and running normally** — the plugin's own code producing an incorrect capability check, a malformed REST response, a broken authentication decision, or any other functional defect during ordinary request handling. This is the condition every generic "Plugin category" citation elsewhere in this repository refers to; it remains a real, valid attribution for those entries' own boundary purposes, but is not itself catalogable as a `WP-ERROR` entry in this taxonomy, since it has no reproducible, plugin-independent mechanism to document. A `WP-ERROR` entry documenting one *specific*, sufficiently common third-party plugin's own defect remains possible in principle (per `WP-ERROR-013` Section 17 and `WP-ERROR-017` Section 17's own single-responsibility disclaimers) but is not part of this taxonomy's initial planned set.
* **Must-use plugin loading and fatal errors** — already fully owned by `WP-ERROR-017`, which predates this taxonomy. See Section 3.
* **A PHP fatal error during a normal (post-bootstrap) request, once a plugin has already loaded successfully** — `WP-ERROR-013`'s own bootstrap-fatal-error entry owns fatal errors occurring *during* the bootstrap sequence itself (including a plugin's own top-level code); this category owns the *lifecycle transition* mechanisms (activation, update) that operate outside, and are distinct from, ordinary per-request bootstrap. A fatal error in an active plugin's normal runtime code, unrelated to any lifecycle transition, remains `WP-ERROR-013`'s condition (or a plugin-specific defect, per the first bullet above) — not this category's.
* **A duplicate function or class declaration between two simultaneously active plugins, discovered during ordinary bootstrap** — already an explicitly named cause within `WP-ERROR-013`'s own Common Causes (Section 10: "a duplicate function or class declaration, commonly caused by a duplicated plugin installation or a duplicated file"). This taxonomy considered, and explicitly declined to duplicate, that territory; see Section 5.
* **A plugin update's own filesystem write failing because the operating system denies the specific access required, or because capacity is exhausted** — already fully owned by `WP-ERROR-019` (Filesystem Permission Denied) and `WP-ERROR-020` (Disk Space Exhausted) respectively, both of which explicitly and by name already document the `wp-content/upgrade` staging directory and the associated directory-creation failure as their own territory, predating this taxonomy. This category does **not** claim any part of that territory: it owns the update *mechanism's* own behavior (package integrity, extraction, the multi-step file-swap process, and automatic-rollback logic) as the diagnostic entry point, and hands off to `WP-ERROR-019`/`020` once diagnosis confirms the specific cause is an OS-level access or capacity constraint rather than a defect in the update mechanism's own process. See Section 3.
* **A plugin update's own outbound download failing to connect, or failing TLS negotiation, when fetching the update package** — already fully owned by `WP-ERROR-028` (Outbound HTTP Request Failure) and `WP-ERROR-029` (Outbound TLS Negotiation Failure) respectively, both of which explicitly name "plugin/theme/core update checks" and the outbound request to `api.wordpress.org` (or an equivalent endpoint) as their own territory, predating this taxonomy. This category does not claim the connection-establishment or TLS-negotiation stage of an update's own download step; it owns what happens once a response is actually received (a corrupt or incomplete downloaded package, an extraction failure) and hands off to `WP-ERROR-028`/`029` where diagnosis confirms the download never actually completed. See Section 3.
* **Plugin-specific filesystem assets in general, unconnected to any lifecycle transition** (a plugin file's content becoming corrupted at rest, independent of any activation or update event) — `SF-TAXONOMY-001` Section 2 excludes "Plugin-specific assets" from Filesystem and assigns them here in principle, but no entry in this taxonomy's initial planned set actually claims this specific, at-rest condition; it remains an undisclosed gap, the same class `WP-ERROR-028` Section 7 established a precedent for disclosing rather than silently absorbing into an adjacent entry.
* **WordPress core's own update mechanism** (updating WordPress itself, as opposed to a plugin) — a related but distinct mechanism (`Core_Upgrader` rather than `Plugin_Upgrader`), out of scope for this category; not currently owned by any entry in this catalog.
* **Theme activation, update, or lifecycle failures** — Theme category, an exact structural parallel WordPress itself maintains (a distinct `Theme_Upgrader` class and separate activation code path) but a conceptually independent category from Plugin, per `SF-SPEC-001` Section 7's own separate `Theme` category value.
* **A missing PHP extension or unsupported PHP version a plugin's own code requires, once verified as the underlying cause** — PHP Runtime category (`WP-ERROR-014`/`015`), the same boundary `WP-ERROR-017` Section 6 already establishes for the must-use case; this category owns the lifecycle mechanism's own behavior (for example, WordPress refusing activation because a declared `Requires PHP` version is unmet), not the underlying PHP-runtime condition itself once the mechanism has correctly identified and reported it.
* **WordPress core corruption affecting the update or activation mechanism's own code** — `WP-ERROR-016`'s own territory; this category presumes WordPress core's own plugin-management code is itself intact and functioning as designed.
* **Malicious code deliberately introduced via a compromised plugin, and the compromise investigation itself** — Security category (once a taxonomy exists for it); this category owns the mechanism's own designed behavior, not a security-incident investigation, though Section 15 of any resulting entry carries the same security-considerations discipline established throughout this catalog.

## 3. Planned Entries

| Entry | Title | Owns | Status |
|---|---|---|---|
| `WP-ERROR-017` | Must-Use Plugin Fatal Error | A PHP fatal error originating from code loaded via the must-use plugin mechanism (`wp-content/mu-plugins/`), distinguished from every other entry in this category by the complete absence of an activation/deactivation toggle or any built-in fatal-error protection, since must-use plugins load unconditionally and the mechanisms Section 3's other two entries own (activation-time protection, the update pipeline) do not apply to them at all. | Existing, Production Ready |
| `WP-ERROR-031` | WordPress Plugin Activation Failure | A verified failure at the specific moment WordPress attempts to activate a regular (non-must-use) plugin: the plugin's own declared requirements (`Requires PHP`, `Requires at least`, `Requires Plugins`) are not met and WordPress refuses to attempt activation at all; a PHP fatal error occurs during the activation-time include of the plugin's own file, which WordPress's own activation-time protection detects and responds to by aborting activation and leaving the plugin inactive rather than leaving a fatally-broken plugin active; or the plugin's own `register_activation_hook()` callback itself fails, throws, or leaves the plugin in a partially-initialized state. Distinct from `WP-ERROR-017` by the presence of this activation-time mechanism and toggle, which must-use plugins entirely lack. | Existing, Production Ready |
| `WP-ERROR-032` | WordPress Plugin Update Failure | A verified failure in WordPress's own plugin-update mechanism (`Plugin_Upgrader`) itself, once a response to the download request has actually been received: the downloaded package is corrupt, incomplete, or fails extraction; the multi-step file-swap process is interrupted for a reason other than an OS-level permission or capacity constraint (for example, an execution-time limit or an externally terminated request, leaving a mixed-version or incomplete set of files); or — for an *automatic* background update specifically — a fatal error is detected immediately afterward and WordPress's own automatic-rollback mechanism (available for automatic updates specifically, not for a manually-triggered "Update Now" action) either succeeds or itself fails to restore the previous version. Owns the update mechanism's own process as the diagnostic entry point; hands off to `WP-ERROR-019`/`020` where the file-swap interruption is confirmed to be a permission or capacity constraint, and to `WP-ERROR-028`/`029` where the download itself is confirmed to have never completed. Distinct from a plugin's own post-update code defect that is not itself a mechanism failure (the update mechanically succeeded; the new code has a bug) — that remains the plugin's own business-logic defect, outside this category's initial planned set per Section 2. | Existing, Production Ready |

Nothing else is currently planned for this category. Any future addition to this table is a revision to this document, not an ad hoc decision made while authoring an unrelated entry, per **SF-SPEC-013** Section 5.7.

## 4. Ownership Model

The three entries divide by **lifecycle stage**, not by a single pipeline or a single "independent conditions" model:

* `WP-ERROR-017` owns the **loading** stage for must-use plugins specifically — a stage with no activation event and no toggle at all, occurring unconditionally on every request.
* `WP-ERROR-031` owns the **activation** stage for regular plugins — a discrete, toggleable event WordPress mediates directly, with its own built-in fatal-error protection and requirement-gating logic that must-use plugins never pass through.
* `WP-ERROR-032` owns the **update** stage for regular plugins — a distinct mechanism (`Plugin_Upgrader`'s own package-integrity, extraction, and file-swap process, and, for automatic updates, rollback logic) that can be reached independently of activation (a plugin can be updated while already active, without a fresh activation event occurring) and that must-use plugins do not participate in via any comparable, WordPress-provided mechanism (a must-use plugin file is typically replaced directly on the filesystem, outside `Plugin_Upgrader` entirely). This entry owns the mechanism's own process, not every possible underlying cause a file-swap step's own failure might trace to — an OS-level permission or capacity constraint remains `WP-ERROR-019`/`020`'s own territory, and a download that never actually completed remains `WP-ERROR-028`/`029`'s own territory, per Section 2.

Unlike `SF-TAXONOMY-004`'s two-axis model (a sequential pair plus one independent entry), these three entries are **three independent lifecycle stages sharing no common precondition chain**: a must-use plugin fatal error, a regular plugin's activation failure, and a regular plugin's update failure are mutually exclusive by construction (a must-use plugin is never activated or updated through either of the other two mechanisms at all) rather than by a shared sequence one must pass through before reaching the next.

**Evidentiary basis for excluding a fourth, "generic plugin defect" entry:** `WP-ERROR-013`, `016`, `022`, `023`, `024`, `026`, and `027` all cite "Plugin category" generically, without naming a specific `WP-ERROR` ID, when attributing a symptom to a specific plugin's own defect. This taxonomy examined that pattern directly (Section 2) and concluded it does not describe a catalogable mechanism-level condition the way every other category's own entries do — it describes the *residual* explanation once every other category's own mechanism has been ruled out, which is precisely why none of those citing entries ever names a specific ID. Declaring a fourth entry to "receive" that residual territory would misrepresent an attribution convention as a documented, reproducible condition it is not.

## 5. Candidates Considered and Rejected

* **A dedicated "Plugin Deactivation Failure" entry:** not given an entry. WordPress's own deactivation mechanism (`deactivate_plugins()`) is a comparatively simple state change (removing an entry from the active-plugins option and firing `register_deactivation_hook()`'s own callback) with a narrow failure surface; the more common real-world pain point — a plugin's own deactivation hook failing to clean up its own data (orphaned cron events, options, or custom tables) — is a plugin-specific business-logic defect under Section 2's own first exclusion, not a WordPress-mechanism failure. No evidence was found that deactivation itself, as a mechanism, fails often or distinctly enough to justify a dedicated entry at this taxonomy's current level of granularity.
* **A dedicated "Plugin Uninstall Failure" entry:** not given an entry, for the same reason as deactivation — the uninstall mechanism itself (`uninstall.php` inclusion, or `register_uninstall_hook()`) is a narrow, low-frequency mechanism, and the common real-world complaint (leftover data after uninstall) is a plugin's own cleanup-logic defect, not a WordPress-mechanism failure.
* **A dedicated "Plugin Conflict / Function-Class Collision" entry:** not given an entry. `WP-ERROR-013` Section 10 already explicitly names "a duplicate function or class declaration, commonly caused by a duplicated plugin installation or a duplicated file" as its own territory. Splitting this out would require the same kind of mechanism-level justification `WP-ERROR-017` had for must-use plugins (no toggle, no protection) — but an ordinary two-plugin collision during bootstrap has neither a distinct mechanism nor a distinct recovery path from `WP-ERROR-013`'s own general bootstrap-fatal-error condition; the fact that the specific cause happens to be "two plugins" rather than "one plugin and a theme" or "a must-use plugin and a drop-in" does not, on its own, create a mechanism-level difference the way must-use loading's total absence of a toggle did. Deferred, not rejected outright — should this specific cause prove disproportionately common relative to `WP-ERROR-013`'s other causes, a future revision to this taxonomy could still carve it out, per **SF-SPEC-013** Section 5.6.
* **A dedicated "Plugin Requirement (`Requires Plugins`) Dependency Chain" entry, separate from Activation Failure:** considered and folded into `WP-ERROR-031` instead of given its own entry. WordPress's own requirement-gating behavior (refusing to even attempt activation when `Requires PHP`/`Requires at least`/`Requires Plugins` are unmet) is, mechanically, a precondition check *of* the activation mechanism, not an independently reachable failure mode with its own separate code path a user could encounter without also being in an activation context — unlike the REST API's own three genuinely independent pipeline stages (route resolution, authentication/authorization, callback execution), which this taxonomy's own three-entry structure does not attempt to mirror unnecessarily.
* **Automatic-update-specific rollback failure as its own entry, separate from Update Failure:** considered and folded into `WP-ERROR-032` instead of given its own entry. The rollback mechanism is a corrective *response* the update mechanism itself invokes upon detecting its own fatal-error condition, not a conceptually independent lifecycle stage; treating it as a distinct cause within `WP-ERROR-032` (per that entry's own future Section 10) is more consistent with how this catalog has handled multi-cause conditions elsewhere (`WP-ERROR-029`'s eight TLS causes within one entry) than splitting it into a fourth entry would be.
