## 2. Category Boundary

**Cron** owns failures in WordPress's own pseudo-cron mechanism ("WP-Cron") — the scheduling, triggering, and event-processing machinery that runs scheduled tasks (`wp_schedule_event()`, `wp_schedule_single_event()`) without relying on a true, OS-level cron daemon by default. It does not own a specific plugin's own scheduled callback containing a business-logic defect, nor any WordPress mechanism a cron-triggered task merely reaches once its own callback begins executing normally.

WP-Cron is unusual among this catalog's categories in a specific way worth stating directly: unlike a system cron job, WordPress's own default triggering mechanism is not time-driven on its own. It is a side effect of ordinary site traffic — on every qualifying page load, WordPress checks whether any scheduled event is due and, if so, fires an asynchronous, non-blocking HTTP request to `wp-cron.php` to process it. This means WP-Cron's own reliability is itself a function of site traffic, a characteristic with no analog anywhere else in this catalog and the source of this category's own most consequential boundary decision (Section 4).

**Explicitly not owned by Cron:**

* **A PHP fatal error occurring during `wp-cron.php`'s own bootstrap sequence, before scheduled-event processing begins** — already fully owned by `WP-ERROR-013`, whose own Section 4/8 already name `wp-cron.php` as sharing the identical bootstrap code path every other entry point (front-end, `wp-admin`, AJAX, REST, WP-CLI) shares, predating this taxonomy. This category owns only what happens *after* that shared bootstrap sequence has already completed successfully — the same "post-bootstrap, this category's own territory" boundary `SF-TAXONOMY-005` Section 2 already draws for Plugin against `WP-ERROR-013`.
* **The connection-establishment mechanics of `wp-cron.php`'s own self-referential "loopback" trigger request** (DNS resolution, TCP connection refusal, a blocked or disallowed destination) — already fully owned by `WP-ERROR-028` (Outbound HTTP Request Failure), whose own transport-agnostic `WP_Http` mechanism the loopback trigger itself uses internally (via `wp_remote_post()`, the same public function ordinary outbound requests use). This category does not re-claim that transport-level mechanism; it owns the *observable*, cron-specific consequence — scheduled events silently not running — and the diagnostic path specific to this failure pattern, which differs sharply from `WP-ERROR-028`'s own diagnostic path because the loopback trigger request is deliberately non-blocking and its own result is never checked or reported by WordPress at all (see Section 4). This category hands off to `WP-ERROR-028` once diagnosis confirms the loopback request's own connection is the specific root cause.
* **A specific plugin's own scheduled callback containing a business-logic defect**, once that callback is confirmed to have actually been invoked and to have executed without a PHP fatal error or a timeout — the direct structural parallel to every prior lifecycle category's own first exclusion (`SF-TAXONOMY-005` Section 2 for Plugin, `SF-TAXONOMY-008` Section 2 for Theme). Not catalogable as a `WP-ERROR` entry in this taxonomy for the same reason: no reproducible, plugin-independent mechanism to document.
* **A missing PHP extension or unsupported PHP version a cron-triggered callback's own code requires, once verified as the underlying cause** — PHP Runtime category (`WP-ERROR-014`/`015`), both of which already name a "scheduled-job runner" as an example SAPI context in their own Diagnosis sections, `WP-ERROR-014`'s own text further elaborating "such as system cron invoking WP-Cron or WP-CLI," predating this taxonomy.
* **A cron-triggered task's own outbound call to a third-party service failing**, once the task's own callback has actually begun executing — already `WP-ERROR-028`'s own territory, whose own Section 9 (Typical Symptoms) already names "WP-Cron-triggered outbound requests (scheduled tasks that call external services)" failing as one of its own example symptoms, predating this taxonomy. This is a different condition from the loopback-trigger-request exclusion above: that exclusion concerns WordPress triggering *itself*; this exclusion concerns a scheduled task's *own* code calling *another* service once it is already running.
* **Increased database load or query timeout from a cron-triggered query**, once the query is confirmed to have actually executed — `WP-ERROR-009`'s own territory, whose own text already names `WP-Cron` as a common, legitimate destination for moving a long-running query out of the ordinary request path, predating this taxonomy.
* **A plugin's own deactivation hook failing to remove a cron event it had scheduled**, leaving an orphaned event — already disclosed as a plugin-specific business-logic gap by `SF-TAXONOMY-005` Section 5's own "Plugin Deactivation Failure" analysis, not a WordPress-mechanism-level condition this category claims.
* **A missed scheduled *post* publication specifically, as a content-workflow feature**, where the underlying cause is this category's own condition (the cron trigger itself not firing) — this category owns the general triggering/execution mechanism regardless of which specific hook was scheduled; a scheduled post failing to publish on time is a symptom of this category's own condition, not a distinct condition of its own requiring a separate, content-specific entry.

## 3. Planned Entries

| Entry | Title | Owns | Status |
|---|---|---|---|
| `WP-ERROR-043` | WordPress Scheduled Cron Event Not Triggered | A verified condition in which a legitimately scheduled WP-Cron event (confirmed present via `wp_next_scheduled()`) fails to fire at or near its intended time, because the triggering mechanism itself — WordPress's own traffic-driven check-and-fire behavior, or a manually configured replacement — never reaches the point of attempting to process due events at all. Causes include an absence of qualifying site traffic (the most common cause on low-traffic sites, since WordPress's own default mechanism has no other trigger), the self-referential loopback request failing to connect, `DISABLE_WP_CRON` being set without a working real-cron replacement actually configured, and WordPress's own concurrency-locking mechanism (`WP_CRON_LOCK_TIMEOUT`) blocking a legitimate new trigger attempt. Owns the triggering mechanism's own failure to reach scheduled-event processing at all; hands off to `WP-ERROR-028` where the loopback request's own connection is confirmed as the specific root cause. | Planned |
| `WP-ERROR-044` | WordPress Scheduled Cron Event Callback Failure | A verified condition in which WP-Cron's own triggering mechanism *did* successfully reach and begin processing due events (distinguishing this entry from `WP-ERROR-043`), but a specific scheduled event's own registered callback fails to complete correctly — a PHP fatal error occurring during the callback's own post-bootstrap execution (not `WP-ERROR-013`'s own territory, which covers only the shared bootstrap sequence preceding event processing), the callback exceeding the PHP execution-time limit governing the cron request, or the event having been scheduled (`wp_next_scheduled()` shows it pending) with no callback actually registered against its own hook name at all. Owns the event-processing stage once triggering has already succeeded. | Planned |

Nothing else is currently planned for this category. Any future addition to this table is a revision to this document, not an ad hoc decision made while authoring an unrelated entry, per **SF-SPEC-013** Section 5.7.

## 4. Ownership Model

The two entries divide by **processing stage**, gated sequentially: `WP-ERROR-043` owns whether scheduled-event processing is ever *reached* at all; `WP-ERROR-044` owns what happens to a *specific event* once processing has actually begun. `WP-ERROR-044`'s own condition is only reachable once `WP-ERROR-043`'s own condition does not apply — the same sequential-but-conditional shape `SF-TAXONOMY-009` established for CLI, though unconditional here rather than gated on an installation-type check: every WP-Cron run that successfully triggers reaches event-processing, unlike CLI's own site-context stage, which applies only to Multisite.

**The central boundary decision this taxonomy makes, stated explicitly:** WordPress's own default triggering mechanism is not a distinct "service" that either runs or doesn't in the way a system cron daemon does; it is entirely a side effect of ordinary page-load traffic, with no independent existence apart from that traffic. This taxonomy treats "an absence of qualifying traffic" as a legitimate cause *within* `WP-ERROR-043`'s own condition, not a separate, excluded condition, because from a site owner's own diagnostic perspective, "my scheduled events aren't running" presents identically regardless of whether the underlying reason is a connectivity failure, a locking conflict, or simply an absence of visits — and a reader arriving at this entry needs all three explained together, in one place, to correctly diagnose which applies.

**Loopback-request diagnostic asymmetry, the second load-bearing technical distinction this taxonomy relies on:** WordPress's own `spawn_cron()` mechanism issues its loopback trigger request as `'blocking' => false`, meaning WordPress never inspects the result, never calls `is_wp_error()` against it, and never surfaces any indication that the request failed. This is a fundamentally different diagnostic posture from `WP-ERROR-028`'s own condition, where a calling function's own failure to check `is_wp_error()` is treated as a caller-side gap in an otherwise-inspectable outcome. Here, the outcome is deliberately never inspected by WordPress itself at all, by design. This is why `WP-ERROR-043` cannot simply defer entirely to `WP-ERROR-028`'s own diagnostic procedure and requires its own distinct diagnostic path, escalating to `WP-ERROR-028` only once the loopback request's own connection-level failure is independently confirmed through means outside WordPress's own (nonexistent) reporting for this specific call.

## 5. Candidates Considered and Rejected

* **A dedicated "Duplicate/Stacked Cron Event" entry**, covering a plugin repeatedly calling `wp_schedule_event()` without first checking `wp_next_scheduled()`: considered and rejected. This is a specific plugin's own coding defect — a well-known, common one, but not a WordPress-mechanism-level condition distinct from Section 2's own first exclusion (a specific plugin's own business-logic defect). WordPress's own scheduling API behaves exactly as documented when called this way; the resulting duplication is the caller's own error, not a defect in the mechanism itself.
* **A dedicated "Missed Scheduled Post Publication" entry**, covering the specific, common user-facing symptom of a scheduled post not going live on time: considered and rejected, per Section 2's own final exclusion bullet. This is a symptom of `WP-ERROR-043`'s own condition (the cron trigger not firing) applied to one specific, common hook (`publish_future_post`), not a distinct mechanism-level condition warranting its own entry — the same reasoning that keeps this taxonomy from creating a separate entry for every individual core or plugin hook that happens to depend on WP-Cron.
* **A dedicated "System Cron Misconfiguration" entry**, covering the specific case of a site owner configuring a real, OS-level cron job to replace WordPress's own default trigger but getting the URL, schedule, or authentication wrong: considered and folded into `WP-ERROR-043` rather than given a separate entry. This is one of several concrete causes of the same observable condition (`WP-ERROR-043`'s own "triggering mechanism never reaches event processing"), not a mechanistically distinct failure mode from the site owner's or a reader's own diagnostic perspective — the same reasoning `SF-TAXONOMY-005` Section 5 applied to fold `Requires Plugins` gating into `WP-ERROR-031` rather than splitting it out.
* **A dedicated "Cron Lock Deadlock" entry**, covering `WP_CRON_LOCK_TIMEOUT` specifically: considered and folded into `WP-ERROR-043` rather than given a separate entry, for the same reasoning as the system-cron-misconfiguration candidate above — one of several causes of the same observable triggering failure, not a separately diagnosable mechanism from a reader's own starting point.
