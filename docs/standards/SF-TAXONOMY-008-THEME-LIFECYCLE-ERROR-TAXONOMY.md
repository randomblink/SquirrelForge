## 1. Purpose

Declare the Theme category's boundary and complete planned `WP-ERROR` entry set *before* any new entry in it is authored, per **SF-SPEC-013** Section 5.1's Category Entry Criteria — resolving `SF-TAXONOMY-005` Section 2's own explicit forward-reference to Theme as "an exact structural parallel WordPress itself maintains (a distinct `Theme_Upgrader` class and separate activation code path) but a conceptually independent category from Plugin." This is the sixth category in this catalog to receive a dedicated taxonomy document from a genuinely zero-entry starting point (after REST API, Authentication, Networking, Caching/Performance, and Media), rather than the mid-stream situation Plugin Lifecycle faced with a pre-existing `WP-ERROR-017`.

This document does not itself contain any `WP-ERROR` knowledge content and is not cited as a `WP-ERROR` entry.

## 2. Category Boundary

**Theme** owns failures in WordPress core's own generic mechanism for managing theme code across its lifecycle — switching (the WordPress term for what this document, following common usage, also calls activation) and update — and the fatal errors or invalid/inconsistent states those specific mechanisms can produce. It does not own arbitrary template-rendering or business-logic defects inside a specific theme's own code, once that theme is running normally through a lifecycle stage that itself completed correctly.

This taxonomy performed a proactive cross-category ownership sweep during drafting, per the practice this project adopted after `WP-ERROR-032`'s own mid-production correction (`SF-TAXONOMY-005` v1.1→v1.2) and validated on Performance and Media: a full-text search across every existing entry for "theme," "switch_theme," "child theme," "Theme_Upgrader," and related terminology, checking each hit for whether it represents an existing entry's own genuine claim on part of this category's intended territory rather than an illustrative mention.

**Explicitly not owned by Theme:**

* **A specific theme's own template-rendering or business-logic defect, once switched to and running normally** — the theme's own code producing an incorrect template output, a broken block pattern, or any other functional defect during ordinary request handling. The direct structural parallel to `SF-TAXONOMY-005` Section 2's own first exclusion for Plugin; not catalogable as a `WP-ERROR` entry in this taxonomy for the same reason (no reproducible, theme-independent mechanism to document).
* **A PHP fatal error in the active theme's own `functions.php`, occurring during the normal (ongoing, every-request) bootstrap sequence, once the theme is already active** — already explicitly and by name owned by `WP-ERROR-013` (Bootstrap PHP Fatal Error), whose own Section 4 already names "the active theme's `functions.php`" as one of the bootstrap-sequence components it covers, and whose own Section 10 (Common Causes) already names "the active theme's `functions.php` raising a fatal error during theme setup" as one of its own causes, predating this taxonomy. This category owns the *lifecycle transition* mechanism (the one-time switching event and its own built-in error handling), not the theme's ongoing, per-request bootstrap execution once already active — the same distinction `SF-TAXONOMY-005` Section 2 draws between `WP-ERROR-013` and the plugin-activation/update mechanisms.
* **A theme update's own filesystem write failing because the operating system denies the specific access required, or because capacity is exhausted** — already fully owned by `WP-ERROR-019` (Filesystem Permission Denied) and `WP-ERROR-020` (Disk Space Exhausted) respectively, both of which already explicitly name "plugin/theme installation or updates" and the shared `wp-content/upgrade` staging directory as their own territory, predating this taxonomy. This category owns the update *mechanism's* own process, not an OS-level access or capacity constraint underlying one of its steps — the identical hand-off `SF-TAXONOMY-005` Section 2 already establishes for Plugin.
* **A theme update's own outbound download failing to connect, or failing TLS negotiation, when fetching the update package** — already fully owned by `WP-ERROR-028` (Outbound HTTP Request Failure) and `WP-ERROR-029` (Outbound TLS Negotiation Failure) respectively, both of which already explicitly name "plugin/theme/core update checks" as their own territory, predating this taxonomy. This category owns what happens once a response to the download request is actually received, not the connection-establishment or TLS-negotiation stage itself — the identical hand-off `SF-TAXONOMY-005` Section 2 already establishes for Plugin.
* **A missing PHP extension or unsupported PHP version a theme's own code requires, once verified as the underlying cause** — PHP Runtime category (`WP-ERROR-014`/`015`), both of which already scope themselves generically to "an active plugin or theme" throughout. This category owns the lifecycle mechanism's own behavior (WordPress refusing a theme switch because a declared `Requires PHP`/`Requires WP` version is unmet), not the underlying PHP-runtime condition itself once the mechanism has correctly identified and reported it — the identical boundary `SF-TAXONOMY-005` Section 2 already establishes for Plugin's own `Requires PHP` gate. Note for the entry that will claim this territory (Section 3): `WP-ERROR-014`/`015`'s own Typical Symptoms sections already anticipate "a plugin or theme activation blocked by a requirements-not-met notice," but each currently cross-references only `WP-ERROR-031` as "the plugin-activation-specific diagnostic entry point" — a narrow, pre-existing completeness gap for the corresponding theme entry's own independent review to close, not a boundary conflict this taxonomy needs to resolve now.
* **WordPress core's own update mechanism** (updating WordPress itself, as opposed to a theme) — `Core_Upgrader` rather than `Theme_Upgrader`, out of scope for this category, the same exclusion `SF-TAXONOMY-005` Section 2 makes for Plugin.
* **Plugin activation, update, or lifecycle failures** — Plugin category (`WP-ERROR-017`/`031`/`032`), the exact structural parallel this taxonomy itself mirrors; `SF-TAXONOMY-005` Section 2 already names Theme as its own reciprocal exclusion.
* **WordPress core corruption affecting the switching or update mechanism's own code** — `WP-ERROR-016`'s own territory; this category presumes WordPress core's own theme-management code is itself intact and functioning as designed.
* **Malicious code deliberately introduced via a compromised theme, and the compromise investigation itself** — Security category (once a taxonomy exists for it); this category owns the mechanism's own designed behavior, not a security-incident investigation.
* **Template hierarchy resolution, the Customizer's own live-preview UI, widgets, and block-theme (`theme.json`, block templates) content** — runtime/rendering concerns downstream of a successful theme switch, not a lifecycle-transition mechanism; considered and deferred rather than assigned an entry in this taxonomy's initial planned set. See Section 5.

## 3. Planned Entries

| Entry | Title | Owns | Status |
|---|---|---|---|
| `WP-ERROR-039` | WordPress Theme Activation (Switching) Failure | A verified failure at the specific moment WordPress attempts to switch the active theme to a specific target theme: the target theme's own declared requirements (`Requires PHP`, `Requires at least`, and, for themes registering it, `Requires Plugins`) are not met and WordPress refuses to attempt the switch at all; WordPress's own theme-integrity check (`WP_Theme::errors()`) detects the target theme is "broken" — a missing or unreadable `style.css`, or, for a child theme, a `Template` header naming a parent theme that is not installed — and refuses the switch; or the target theme's own `after_switch_theme` callback itself fails, throws, or leaves the site in a partially-initialized state after the switch has otherwise completed. The direct structural parallel to `WP-ERROR-031`'s own three-cause structure for plugin activation. | Existing, Production Ready |
| `WP-ERROR-040` | WordPress Theme Update Failure | A verified failure in WordPress's own theme-update mechanism (`Theme_Upgrader`, sharing the same `WP_Upgrader` base class and `wp-content/upgrade` staging directory `Plugin_Upgrader` uses) itself, once a response to the download request has actually been received: the downloaded package is corrupt, incomplete, or fails extraction; the multi-step file-swap process is interrupted for a reason other than an OS-level permission or capacity constraint; or — for an *automatic* background update specifically — a fatal error is detected immediately afterward and WordPress's own automatic-rollback mechanism either succeeds or itself fails to restore the previous version. The direct structural parallel to `WP-ERROR-032`'s own three-cause structure for plugin update, owning the update mechanism's own process as the diagnostic entry point and handing off to `WP-ERROR-019`/`020` and `WP-ERROR-028`/`029` on the same terms `WP-ERROR-032` already establishes. | Planned |

Nothing else is currently planned for this category. Any future addition to this table is a revision to this document, not an ad hoc decision made while authoring an unrelated entry, per **SF-SPEC-013** Section 5.7.

## 4. Ownership Model

The two entries divide by **lifecycle stage**, the same model `SF-TAXONOMY-005` established for Plugin, narrowed here to two stages rather than three since Theme has no must-use-equivalent mechanism (WordPress has exactly one active theme at a time, with no unconditionally-loaded, toggle-free theme analogous to a must-use plugin):

* `WP-ERROR-039` owns the **switching** stage — a discrete, toggleable event WordPress mediates directly (exactly one theme is active at any time; switching to a new theme is simultaneously the deactivation of the old one and the activation of the new one, an atomic transition with no independently-reachable "deactivation" failure mode of its own, unlike Plugin's separately toggleable activate/deactivate pair), with its own built-in requirement-gating and broken-theme detection.
* `WP-ERROR-040` owns the **update** stage — a distinct mechanism (`Theme_Upgrader`'s own package-integrity, extraction, and file-swap process, and, for automatic updates, rollback logic) reachable independently of switching (a theme can be updated while inactive, without any switch event occurring at all), sharing its underlying `WP_Upgrader` machinery with `Plugin_Upgrader` but operating on theme packages and the theme-specific portion of the `wp-content/upgrade` staging directory.

These two entries are **mutually exclusive by construction**: a theme-switch attempt and a theme-update attempt are distinguishable, separately-triggered WordPress actions with no overlapping code path, the same structural relationship `WP-ERROR-031`/`032` already have.

**Structural difference from Plugin, noted explicitly:** Plugin's own three-entry set includes `WP-ERROR-017` (Must-Use Plugin Fatal Error) because must-use plugins load unconditionally with no activation toggle and no built-in fatal-error protection, a mechanism genuinely absent for themes — WordPress has no "must-use theme" concept, and the single active theme's `functions.php` fatal-error case is already `WP-ERROR-013`'s own territory (Section 2). This taxonomy's two-entry set is not an incomplete mirror of Plugin's three; it is the complete set the actual, narrower set of distinct Theme-specific mechanisms supports.

## 5. Candidates Considered and Rejected

* **A dedicated "Theme Deactivation Failure" entry:** not given an entry, and not merely folded into `WP-ERROR-039` as Plugin's `Requires Plugins` gating was — themes have no independently-reachable deactivation mechanism at all (see Section 4); the switch itself is the only relevant event.
* **A dedicated "Theme Deletion/Uninstall Failure" entry:** not given an entry, for the same reason as Plugin's own uninstall exclusion (`SF-TAXONOMY-005` Section 5) — `delete_theme()`'s own failure surface is narrow and traces to an OS-level permission or capacity constraint already owned by `WP-ERROR-019`/`020`, not a distinct mechanism-level condition.
* **A dedicated "Child Theme / Parent Theme Relationship" entry, separate from Activation (Switching) Failure:** considered and folded into `WP-ERROR-039` instead of given its own entry, for the same reasoning `SF-TAXONOMY-005` Section 5 applied to Plugin's `Requires Plugins` gating — a missing-parent condition is, mechanically, one of the specific ways WordPress's own broken-theme detection can refuse a switch, not an independently reachable failure mode with its own separate code path.
* **A dedicated "Customizer Live-Preview Switch Failure" entry:** deferred, not given an entry. The Customizer's own AJAX-driven live-preview mechanism is a distinct *interface* for reaching a theme switch, but the underlying failure modes when something goes wrong (a requirement-gate refusal, a broken-theme detection) are the same conditions `WP-ERROR-039` already owns — not a mechanistically distinct condition warranting a separate entry at this taxonomy's current level of granularity.
* **A dedicated "Template Hierarchy / Missing Template File" entry:** rejected, per Section 2's own exclusion — this is theme runtime/rendering territory, structurally parallel to Plugin's own exclusion of "a specific plugin's own business-logic defect once loaded and running normally," not a lifecycle-transition mechanism.
* **A dedicated "Block Theme / `theme.json` Failure" entry:** deferred, not rejected outright. Full Site Editing's `theme.json` and block-template mechanism is comparatively new and this taxonomy found no established, catalog-worthy failure pattern distinct from ordinary theme switching or update (an invalid `theme.json` most commonly manifests as a rendering/runtime defect within an already-active theme, Section 2's own exclusion, rather than a switching- or update-mechanism failure). Disclosed as a genuinely undecided gap, the same class of disclosure `WP-ERROR-028` Section 7 and `SF-TAXONOMY-006` Section 7 established a precedent for — a future revision to this taxonomy could still carve it out per **SF-SPEC-013** Section 5.6 if evidence accumulates that it warrants one.
