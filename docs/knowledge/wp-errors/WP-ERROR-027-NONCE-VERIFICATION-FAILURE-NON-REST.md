# WP-ERROR-027 — WordPress Nonce Verification Failure, Non-REST

---

# 1. Knowledge Entry

WordPress Nonce Verification Failure, Non-REST

---

# 2. Metadata

* **Error ID:** `WP-ERROR-027`
* **Title:** WordPress Nonce Verification Failure, Non-REST
* **Category:** Authentication
* **Severity:** Critical
* **Recovery Priority:** Immediate
* **Status:** Production Ready
* **Version:** 1.0

---

# 3. Summary

**A WordPress nonce is not authentication, authorization, or replay prevention. It is a time-limited request-intent check tied to a specific action and user context.** WordPress has already accepted the user's authentication state, and the user may hold every capability the requested action requires, but a non-REST request is rejected because `wp_verify_nonce()` — directly, or via `check_admin_referer()`/`check_ajax_referer()` — determines the submitted nonce does not match the expected action, user, and timing context.

---

# 4. Primary Failure Mode

A non-REST request (an admin-side form submission, an admin-ajax call, or an equivalent action URL) carries a nonce value, and WordPress's own verification of that value — against the specific action string the handler expects, the requesting user's ID, that user's current session token, and the nonce's own tick-based expiry window — fails, causing the request to be rejected, independent of whether the user's identity (`WP-ERROR-024`), session (`WP-ERROR-025`), or capability (`WP-ERROR-026`) are valid.

---

# 5. Severity

This entry is classified **Critical**, with impact ranging depending on scope:

- Where a single request's own nonce is stale or mismatched (a user left a form open too long, or a specific action's own nonce field was overlooked by custom code), the impact is narrow: that one action fails while every other function continues to work.
- Where the underlying cause is systemic — a full-page or object cache serving stale markup containing an expired or wrong-user nonce to many visitors simultaneously, or a site-wide clock/timing misconfiguration — every write-action across the admin area can fail simultaneously for every user, even though every user's own authentication and authorization remain entirely correct.
- This entry remains classified at the level of its most severe possible manifestation, consistent with the range-based Critical classification used elsewhere in this catalog (`WP-ERROR-021`, `024`, `025`, `026`).

---

# 6. Distinction

This entry applies only when verified evidence establishes that authentication and authorization are **not** the cause of the rejection — the user is confirmed logged in with a currently-valid session and holds whatever capability the action requires — and that the rejection is specifically a nonce-verification failure.

**What a nonce is, precisely, and what it is not:** a WordPress nonce (`wp_create_nonce()`/`wp_verify_nonce()`) is a keyed hash of an action string, the current (or anonymous, `0`) user ID, and that user's current logged-in session token, valid across a rolling time window (a "tick," 12 hours by default, with a nonce remaining acceptable across its own tick and the immediately preceding one — roughly a 12-to-24-hour window, filterable via the `nonce_life` filter). It is **not** a login credential, **not** a capability grant, and — despite common assumption — **not** a single-use, replay-preventing token in the classical CSRF-token sense: the *same* nonce value remains valid for every request made within its own tick window, not only the first. Its actual purpose is narrower: confirming that the specific request currently being processed was genuinely generated by WordPress itself, for this specific action, for this specific user, within a recent, bounded time window — a request-intent and request-origin check, not an identity or permission check.

It is distinct from:

- **`WP-ERROR-024` — WordPress Login Authentication Failure**: credentials were rejected. This entry presumes credentials were already accepted; a nonce failure carries no information about whether the submitted credentials, if any were resubmitted, would themselves be valid.
- **`WP-ERROR-025` — WordPress Authentication Cookie Invalid or Expired**: the authentication cookie or login session itself was not accepted. This entry presumes the session is currently valid — though note that a nonce is itself partly derived from the user's own session token (Section 8), so a session that *changes* (a fresh login, a forced logout-everywhere-else) between nonce generation and verification will correctly invalidate nonces generated under the old session, which is this entry's own condition, not `WP-ERROR-025`'s. Classification follows `SF-TAXONOMY-003` Section 4's explicit rule for this exact overlap: if the *current* session/cookie itself is rejected, `WP-ERROR-025` applies; if the current session is accepted but the submitted nonce does not match that session's own user context, this entry applies.
- **`WP-ERROR-026` — WordPress Capability or Role Authorization Denied**: the authenticated user lacks the required capability. This entry presumes the user holds whatever capability the action requires; a nonce check and a capability check are independent gates that a given handler may evaluate in either order, or even omit one of, depending entirely on how that specific handler's own code is written.
- **`WP-ERROR-022` — WordPress REST API Access Denied**: nonce and authentication behavior inside a REST API request follow a separate boundary — the `X-WP-Nonce` header, the reserved `wp_rest` action string, and REST's own cookie-authentication requirement are all REST-specific mechanisms this entry does not cover. A nonce failure occurring during REST request handling belongs to `WP-ERROR-022`, not here, even though both entries' underlying nonce mechanism is the same `wp_verify_nonce()` function.
- **CSRF or request-verification systems implemented entirely by a plugin, independent of WordPress's own nonce API** (Plugin category): a plugin that rolls its own token-based request-verification scheme, rather than calling `wp_create_nonce()`/`wp_verify_nonce()`/`check_admin_referer()`/`check_ajax_referer()`, produces a condition this entry does not own, regardless of how similar the symptom looks. This entry covers only failures that occur through WordPress's own standard nonce APIs.

---

# 7. Scope

**Covered:** A verified condition in which a non-REST request, submitted by a user whose authentication and authorization are independently confirmed valid, is rejected because WordPress's own nonce-verification mechanism (`wp_verify_nonce()`, `check_admin_referer()`, or `check_ajax_referer()`) determines the submitted nonce does not match the expected action, user and session context, or timing window.

**Excluded:**

- The original credential check failing (`WP-ERROR-024`).
- The authentication cookie or session itself being invalid or unaccepted (`WP-ERROR-025`).
- A capability or role check denying an otherwise-valid, correctly-nonce-verified request (`WP-ERROR-026`).
- Nonce or authentication behavior within REST API request handling (`WP-ERROR-022`).
- A plugin's own independent CSRF/request-verification system that does not call WordPress's own nonce functions.
- A missing PHP extension or unsupported PHP version preventing the nonce-hashing code from executing at all (PHP Runtime category).

---

# 8. WordPress Components

Listed as components commonly involved, not as a claim that every installation exercises every one of them:

- `wp_create_nonce( $action )` (`wp-includes/pluggable.php`), which generates a nonce as a keyed hash of the given action string, the current user's ID (`0` for a logged-out/anonymous context), the current user's own session token (empty string if not logged in), and the current nonce "tick."
- `wp_verify_nonce( $nonce, $action )`, which independently recomputes the expected hash for the current tick and the immediately preceding tick, and returns `1` (current tick), `2` (previous tick — informatively signaling the nonce is older but still within its valid window), or `false` if neither matches. Custom code comparing this return value with strict equality against `true` (`wp_verify_nonce(...) === true`) will incorrectly treat every valid nonce as invalid, since the function never returns literal `true` — see Section 10.
- `wp_nonce_tick()`, which computes the current tick number from the current time and the `nonce_life` filter (default 86400 seconds, split into two 12-hour ticks), determining the effective validity window.
- `check_admin_referer( $action, $query_arg )`, the standard wrapper for admin-side POST form submissions, which verifies the nonce and additionally checks the HTTP `Referer` header, calling `wp_nonce_ays()` (the "Are you sure you want to do this?" screen) on failure unless the caller overrides that behavior.
- `check_ajax_referer( $action, $query_arg, $die )`, the equivalent wrapper for `admin-ajax.php` requests, checking a nonce supplied via `$_REQUEST` (or a specified field/header) and, by default, terminating the request on failure.
- `wp_nonce_field( $action, $name )`, which renders the hidden form field (default name `_wpnonce`) a standard admin form submission carries, and `wp_nonce_url( $actionurl, $action, $name )`, which appends an equivalent nonce as a URL query parameter for action links.
- The `nonce_life` filter, allowing a site or plugin to shorten or lengthen the default validity window.

---

# 9. Typical Symptoms

- WordPress's own "Are you sure you want to do this? Please try again." screen (`wp_nonce_ays()`), typically shown for a failed `check_admin_referer()` call on a standard admin form submission.
- An `admin-ajax.php` request returning `-1` or `0` with no further detail, or a JavaScript-side error handler reporting a failed AJAX call with no descriptive server-side message.
- An action silently appears to do nothing — the page reloads or the request completes at the HTTP level, but the intended change (a saved setting, a deleted item, a triggered action) never actually occurs, because custom code checked the nonce result incorrectly (Section 10) and silently returned early.
- The condition reproduces reliably after a page has been open for an extended period (approaching or exceeding the nonce's own validity window) but not immediately after a fresh page load.
- The condition affects many or all users simultaneously and unpredictably, correlating with a caching layer's own cache-hit pattern rather than with any individual user's own session timing — a signal of stale cached markup (Section 10) rather than an individual timing issue.

---

# 10. Common Causes

Causes are grouped by category, and are deliberately kept separate from one another, since the corrective action differs materially between them. Inclusion in this list identifies a category as plausible; it does not assert that any specific cause is present without diagnostic confirmation.

- **Missing nonce field or header entirely** — the request was assembled (by custom markup, a modified template, or a hand-built AJAX call) without including the nonce value WordPress's own verification function expects to find at all.
- **Wrong nonce action string** — the string passed to `wp_create_nonce()` at generation time does not exactly match the string passed to `wp_verify_nonce()`/`check_admin_referer()`/`check_ajax_referer()` at verification time; the two are hashed independently and are required to match exactly, including any dynamic portion (for example, an appended post ID).
- **Wrong field name passed to verification** — the nonce was generated and rendered under one field or parameter name, but the verification call was configured to look for a different name (a common source of confusion between the default `_wpnonce` and a custom name a plugin's own AJAX handler expects).
- **Expired nonce tick** — the request was submitted after the nonce's own validity window (Section 8) had genuinely elapsed, whether from ordinary user delay or from a server-side clock discrepancy affecting the tick calculation.
- **Nonce generated for a different user or authentication state than the one submitting it** — for example, a nonce rendered into markup while the visitor was logged out (`uid = 0`) is submitted after that same browser tab later logs in, or a nonce tied to one user's own session token is submitted after a forced session invalidation (a password change, a "Log Out Everywhere Else" action) changed that token.
- **Cached markup serving a stale nonce** — a full-page cache, object cache, or CDN serves a previously-rendered page (and the nonce embedded in it at render time) to a different visitor, a different session, or simply after enough time has passed that the embedded nonce's own tick has expired, independent of when the *page* was cached.
- **A request assembled against one screen or action but submitted to a different one** — a nonce genuinely valid for its own originally-intended action is reused, whether by copy-pasted code, a misconfigured bulk action, or a template reused across contexts without updating its own action string, against a handler expecting a different action.
- **Custom code misinterpreting `wp_verify_nonce()`'s own return value** — most commonly, a strict-equality comparison against `true` (`if ( wp_verify_nonce( $nonce, $action ) === true )`), which always evaluates false, since the function's own successful return values are the integers `1` and `2`, never the literal boolean `true`.
- **Verification performed before the expected user context is fully established** — a nonce check executed too early in a request's own lifecycle (for example, before `wp_authenticate()`/session validation has completed, or via a hook that fires before the current user is fully loaded) validates against an incorrect (often anonymous, `uid = 0`) user context rather than the actual requesting user.

---

# 11. Diagnosis

Diagnose in this order — confirm the broadest, most foundational facts first, then compare nonce generation and verification as a matched pair:

1. Confirm the request actually reached its intended handler — rule out a routing, bootstrap, or REST-context (`WP-ERROR-022`) condition presenting a superficially similar rejection.
2. Confirm authentication and authorization are genuinely not the cause: independently verify the user's login/session state (`WP-ERROR-024`/`025`) and, separately, that the user holds the capability the action would require if the nonce check were to succeed (`WP-ERROR-026`) — a nonce failure is easy to misdiagnose when one of these other, unrelated conditions is actually present instead.
3. Only once both are confirmed, compare the nonce's own **generation** and **verification** as a matched pair, checking each of the following individually rather than assuming they match:
   - **Action string** — the exact string passed to `wp_create_nonce()`/`wp_nonce_field()`/`wp_nonce_url()` at generation, character-for-character, against the exact string passed to `wp_verify_nonce()`/`check_admin_referer()`/`check_ajax_referer()` at verification.
   - **Field/parameter name** — the name the nonce was rendered under against the name verification code actually reads from `$_REQUEST`/a custom header.
   - **User context** — the user ID and session-token state at the moment of generation against the user ID and session-token state at the moment of verification; confirm neither changed unexpectedly between the two (a login, logout, or forced session invalidation in between).
   - **Timing** — the elapsed time between generation and submission against the nonce's own effective validity window (Section 8), including whether server clock skew could affect the tick calculation.
   - **Request transport** — confirm the nonce value actually observed server-side, at the point of verification, matches what was genuinely rendered/generated — inspect the actual submitted request (form data or AJAX payload) rather than assuming the client-side code sent what the template intended.
4. Where the condition affects multiple or all users simultaneously, prioritize investigating a caching layer's own handling of nonce-embedded markup over any individual timing or user-context explanation.
5. Where custom code is involved, inspect its own handling of `wp_verify_nonce()`'s return value for the strict-equality-against-`true` defect named in Section 10.
6. Preserve relevant evidence — the exact action string and field name used on both sides, the elapsed time between page render and submission, and whether the condition is single-user or site-wide — before modifying any nonce-generating or nonce-verifying code.

```text
# Example only — illustrates checking a nonce's own validity directly;
# exact usage depends on the specific action string and context involved.
wp eval 'var_dump( wp_verify_nonce( $_REQUEST["_wpnonce"] ?? "", "my_action" ) );'
```

# 12. Recovery Procedure

Recovery shall correct the specific, verified mismatch identified in Diagnosis (Section 11) — generation, transport, caching, action naming, or verification placement — while preserving the nonce check itself.

**Disabling or bypassing nonce verification is not a permitted recovery action for this entry**, regardless of how convenient it may appear as a shortcut; a nonce check that has been removed or made unconditionally permissive no longer provides the request-intent verification it exists for, for every future request, not only the one being diagnosed.

Permitted recovery categories, depending on the verified cause, include:

- Correcting a mismatched action string or field name so generation and verification refer to the same value.
- Ensuring markup containing a nonce is excluded from full-page or object caching, or that any cache serving such markup has a sufficiently short lifetime relative to the nonce's own validity window.
- Correcting custom code that misinterprets `wp_verify_nonce()`'s own return value (using a loose falsy check, `if ( ! wp_verify_nonce( ... ) )`, rather than strict comparison against `true`).
- Moving a misplaced nonce-verification call to occur after the expected user context (authentication and session state) is fully established.
- Regenerating and re-rendering a nonce where the underlying page or form was held open long enough to genuinely exceed the validity window, as an expected, correct outcome rather than a defect — distinguishing this from a systemic caching or generation cause.
- Where a request is legitimately assembled from one screen and submitted to a different handler by design, ensuring both sides deliberately agree on a single, shared action string rather than treating the mismatch as accidental.

---

# 13. Validation

Recovery is successful when:

- The specific, previously-failing action completes successfully for the affected user, with `wp_verify_nonce()` (or the wrapper function in use) returning a non-`false` result for a freshly-generated, correctly-submitted request.
- The correction is confirmed effective across the nonce's own full intended validity window, not only immediately after a fresh page load — testing near the edge of the window where relevant.
- Where a caching-layer correction was made, a fresh request confirms no stale, previously-cached nonce is served to a new visitor or session.
- Where a code-level correction was made (action string, field name, return-value handling, verification placement), the fix is confirmed not to have altered the nonce check's own security properties — it still genuinely rejects a mismatched or forged nonce, not only accepts a matching one.
- No unrelated nonce-protected action was disturbed by the correction.
- The nonce-verification check itself remains present and enforced; recovery did not, at any point, involve removing or unconditionally bypassing it.

---

# 14. Prevention

- Keep a single, consistent action-string and field-name convention between a nonce's own generation and verification call sites, ideally defined once (a constant or shared function) rather than duplicated as literal strings in two places.
- Exclude any markup containing a rendered nonce from full-page and object caching, or ensure cache lifetimes are deliberately kept short relative to the nonce's own validity window.
- Use the standard `wp_verify_nonce()` falsy-check idiom (`if ( ! wp_verify_nonce( ... ) )`) consistently in custom code, rather than a strict-equality comparison against `true`.
- Where a form or action may remain open for an extended period (a long editorial session, a slow connection), consider a shorter user-facing timeout warning rather than relying solely on the nonce's own default validity window to communicate expiry gracefully.
- Test nonce-protected actions explicitly across a login/logout transition and after a forced session invalidation, since both legitimately change the session token a nonce is partly derived from.
- Audit nonce verification call placement relative to authentication/session-establishing code whenever custom request-handling logic is added, to avoid verifying against an incorrect, prematurely-anonymous user context.

---

# 15. Security Considerations

- A nonce failure being easy to work around by disabling verification (Section 12) is itself the security risk this entry's own recovery discipline exists to prevent; the check's entire purpose is defeated the moment it is bypassed rather than corrected.
- Because a WordPress nonce is not single-use (Section 6), it does not by itself prevent a legitimate, captured request from being resubmitted within its own validity window; sites requiring genuine single-use replay prevention for a specific sensitive action need an additional, purpose-built mechanism, not a stronger reliance on the nonce alone.
- A nonce generated for one user and successfully verified under a different user's session — if this is ever observed — is a more serious finding than an ordinary mismatch, and should be investigated as a potential session-handling or caching-layer security defect (a cross-user cache-serving condition, distinct from but potentially overlapping with `WP-ERROR-025`'s own security considerations regarding cached authentication cookies), not merely logged as routine nonce-troubleshooting noise.
- `check_admin_referer()`'s additional `Referer`-header check is a real, complementary security control alongside the nonce itself; a recovery action shall not disable or loosen that check as a substitute for correctly diagnosing and fixing the actual nonce mismatch.

# 17. Notes

This entry documents the general, verified observable condition of WordPress's own standard nonce-verification mechanism rejecting a non-REST request from an otherwise validly authenticated and authorized user. Per explicit direction, it opens by stating plainly what a nonce is not (authentication, authorization, or classical single-use replay prevention) before describing what it actually is, since this misconception is a common source of misdiagnosis this entry exists to correct.

This entry does not own a plugin's own independent CSRF/request-verification system that does not call WordPress's own nonce API; per Section 6, such a system belongs to the Plugin category.
