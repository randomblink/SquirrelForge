# SquirrelForge WordPress Architecture Standard

## Purpose

This document defines the architectural principles that all WordPress plugins, themes, and supporting components generated by SquirrelForge must follow.

The objective is to produce software that is maintainable, testable, secure, extensible, and understandable throughout its lifecycle.

---

# Core Principles

Every project should be:

- Modular
- Predictable
- Maintainable
- Testable
- Secure
- Extensible
- Loosely coupled
- Highly cohesive

---

# Separation of Responsibilities

Each component should have one primary responsibility.

Typical responsibilities include:

- Bootstrap
- Configuration
- Settings
- Assets
- Database
- REST API
- AJAX
- Admin UI
- Frontend UI
- Business Logic
- Validation
- Logging
- Scheduling

No class should perform multiple unrelated responsibilities.

---

# Layered Architecture

SquirrelForge plugins should be organized into logical layers.

```text
Presentation
↓
Controllers
↓
Services
↓
Repositories
↓
WordPress APIs
```

Business logic should remain independent of presentation whenever practical.

---

# Dependency Direction

Dependencies should move downward.

Presentation should depend on Services.

Services should depend on Repositories.

Repositories interact with WordPress.

Avoid circular dependencies.

---

# Class Design

Classes should:

- Have one responsibility.
- Expose a minimal public API.
- Hide implementation details.
- Be easy to replace.
- Be easy to test.

---

# Method Design

Methods should:

- Perform one task.
- Have descriptive names.
- Return predictable values.
- Avoid hidden side effects.
- Remain reasonably short.

---

# Configuration

Configuration belongs in:

- constants
- configuration classes
- WordPress options

Configuration should never be scattered throughout the codebase.

---

# Business Logic

Business rules should not be embedded inside:

- templates
- views
- CSS
- JavaScript
- hook registration

Business logic belongs in dedicated service classes.

---

# Data Access

Database access should be isolated.

Repositories should:

- retrieve data
- save data
- update data
- delete data

Controllers should not contain SQL.

---

# Error Handling

Errors should:

- be logged
- fail safely
- provide meaningful diagnostics
- avoid exposing sensitive information

---

# Extensibility

Projects should expose extension points through:

- actions
- filters
- interfaces
- service registration

Avoid requiring modifications to core project files.

---

# Documentation

Each architectural component should explain:

- its purpose
- responsibilities
- dependencies
- extension points

---

# Review Checklist

Verify that:

- responsibilities are separated
- dependencies flow correctly
- classes are cohesive
- methods are focused
- business logic is isolated
- data access is isolated
- architecture supports future growth

---

# Rule

SquirrelForge must generate WordPress projects that prioritize long-term maintainability over short-term convenience. Architectural consistency is a required quality gate for every generated project.
